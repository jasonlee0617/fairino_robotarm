# ROS Python 标定节点段错误排查

[返回技术文档中心](../README.md)

本文处理一种典型故障：标定节点已看到 MoveIt、Topic 或 Action 就绪，随后没有 Python traceback，而是直接以 `Segmentation fault` 退出。此类问题通常发生在 Python 二进制扩展层，不能只按普通业务异常排查。

## 1. 先确认故障类型

仿真入口：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch myrobot_simulation calibration_sim.launch.py
```

如果节点出现类似以下日志后直接退出：

```text
MoveIt is ready: state=IDLE, plan_service=True, execute_action=True, joint_state=True
Segmentation fault
```

先记录：

- 完整启动命令和退出码；
- `numpy`、`cv2`、`cv_bridge` 的来源；
- 是否存在 `$HOME/.local/lib/python3.10/site-packages`；
- 当前 shell 是否启用了 Conda、venv 或 `pip --user` 包；
- `use_sim_time` 与 `/clock` 是否一致。

## 2. 高概率根因

ROS 2 Humble 的 Python 图像链通常依赖系统安装的 NumPy、OpenCV 与 `cv_bridge`。如果 shell 优先加载 `$HOME/.local`、Conda 或其他环境中的二进制包，可能形成 ABI 不一致：

```text
rclpy / cv_bridge / geometry_msgs
        ↕
系统 OpenCV、NumPy
        ↕  被用户环境中的不同版本替换
用户 site-packages / Conda
```

这类冲突不一定抛出 `ImportError`，也可能在第一次图像转换、TF、MoveIt 或 native 回调时直接崩溃。

线程、驱动和底层库问题也可能导致段错误，因此“用户包污染”是优先检查项，不是对所有段错误的无条件结论。

## 3. 检查实际导入来源

在启动 ROS 节点的同一个终端执行：

```bash
python3 -c "import sys, numpy, cv2; \
print(sys.executable); print(numpy.__file__); print(cv2.__file__)"
python3 -m site
```

ROS Humble 的系统包通常位于：

```text
/usr/lib/python3/dist-packages/
```

如果输出指向 `$HOME/.local`、Conda 或项目虚拟环境，先在干净 shell 中复现：

```bash
env -i HOME="$HOME" USER="$USER" TERM="$TERM" PATH="/usr/bin:/bin" \
  bash --noprofile --norc
source /opt/ros/humble/setup.bash
source install/setup.bash
export PYTHONNOUSERSITE=1
python3 -c "import numpy, cv2; print(numpy.__file__); print(cv2.__file__)"
```

不要在尚未确认包来源前直接调整标定参数或 MoveIt 路点。

## 4. 当前仓库的防护

以下 Launch 当前显式设置 `PYTHONNOUSERSITE=1`：

- `myrobot_simulation/launch/calibration_sim.launch.py`；
- `hand_eye_calibration/launch/calibrate.launch.py`；
- `hand_eye_calibration/launch/assisted_calibration.launch.py`；
- `hand_eye_calibration/launch/auto_calibration_collector_launch.py`。

因此应优先通过 Launch 启动完整标定链。直接使用 `ros2 run hand_eye_calibration auto_calibration_collector.py` 时，调用者需要自行保证 Python 环境干净。

`use_sim_time` 由 `auto_calibration_collector_params.yaml` 管理：

- Gazebo 使用 `true`，并且必须存在 `/clock`；
- 真实机械臂使用 `false`；
- 不要同时依赖 YAML 和临时命令行覆盖形成两套来源。

## 5. 恢复方法

### 临时隔离

先用系统 Python 和禁用 user-site 的 shell 验证：

```bash
export PYTHONNOUSERSITE=1
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch myrobot_simulation calibration_sim.launch.py
```

如果故障消失，说明环境污染证据很强。

### 长期处理

- ROS 工作区优先使用 Ubuntu/ROS 提供的 Python 包；
- 非 ROS 视觉实验放入独立 venv 或 Conda 环境；
- 不在 ROS shell 中使用 `pip install --user` 覆盖 NumPy、OpenCV、SciPy 等二进制依赖；
- 删除包前先用 `python3 -m pip show <package>` 确认位置，不要误删系统或其他项目环境；
- 如果必须使用自定义 Python 环境，应重新构建并验证整套 ROS 二进制依赖，而不是混用现成扩展。

本文不提供自动卸载命令，因为不同主机的包归属不同，盲目卸载可能破坏其他项目。

## 6. 仍然崩溃时

环境来源一致后，继续收集 native 证据：

```bash
ulimit -c unlimited
PYTHONFAULTHANDLER=1 ros2 launch myrobot_simulation calibration_sim.launch.py
```

同时检查：

1. `dmesg` 或 system journal 中的崩溃库名；
2. core dump 的 backtrace；
3. 最小化到 ArUco、`cv_bridge`、MoveIt 或 collector 中的哪一步；
4. 相同输入在系统 Python 下是否稳定；
5. 是否只有多线程执行器或图像回调并发时触发。

只有 backtrace 指向业务节点后，才应修改节点并发或生命周期逻辑。

## 7. 验收

修复后依次确认：

```bash
python3 -c "import numpy, cv2; print(numpy.__file__); print(cv2.__file__)"
ros2 topic list | grep -E 'clock|camera|aruco'
ros2 launch myrobot_simulation calibration_sim.launch.py
```

验收标准：

- Python 扩展来自预期环境；
- `use_sim_time` 与 `/clock` 一致；
- 节点不会在 MoveIt ready 后直接段错误；
- ArUco、TF、采样和求解仍需按[手眼标定操作说明](手眼标定文档说明.md)分别验证。

上述结果只能证明该 native crash 已消失，不能证明标定精度或真实机械臂安全已经验收。
